# Профили Python и Node.js в рабочих папках

## Область действия

Профиль принадлежит одной рабочей папке и выполняется только внутри её Rootfs. Android, Root, Termux, другие рабочие папки и файлы проектов не изменяются. Состояние хранится в метаданных рабочей папки в `.workspace-profiles.json`, а не в `/workspace` или `.venv`.

Поддерживаются Rootfs с точным `ID=ubuntu` или `ID=debian` в `os-release`; `ID_LIKE` сам по себе поддержку не даёт. Для остальных дистрибутивов отображается «Дистрибутив пока не поддерживается», а `apt` не запускается. Основной проект по умолчанию использует Ubuntu 24.04.

Если Rootfs отсутствует или повреждён, интерфейс предлагает существующую установку/восстановление Linux. Rootfs автоматически не переустанавливается. Общий `apt-get upgrade` и `dist-upgrade` не используются.

## Подготовка и источники

Перед установкой выполняется полная функциональная проверка существующего окружения. Исправное окружение используется повторно, без переустановки и без скачивания.

Python устанавливается из штатных репозиториев дистрибутива:

```sh
apt-get update
apt-get install -y --no-install-recommends python3 python3-venv python3-pip
```

Для Node.js допускается существующая поддерживаемая LTS major 22 или 24 с npm. Если её нет, после проверки архитектуры используется официальная фиксированная сборка **Node.js v24.22.1 (LTS Krypton), npm 11.19.1**. Перед распаковкой скачиваются `ca-certificates` и `xz-utils` из штатных репозиториев.

Официальные источники Node.js:

- метаданные релизов: `https://nodejs.org/dist/index.json`;
- контрольные суммы: `https://nodejs.org/dist/v24.22.1/SHASUMS256.txt`;
- arm64: `https://nodejs.org/dist/v24.22.1/node-v24.22.1-linux-arm64.tar.xz`;
- x64: `https://nodejs.org/dist/v24.22.1/node-v24.22.1-linux-x64.tar.xz`.

Закреплённые SHA-256:

- arm64: `dbabf7a1cbf947e6059ffad2c27b80041db97dea1e553b62afdee7f13fca336e`;
- x64: `6c172a9ab6718f7b801fb5a7bd486af2ee5e32758086a04b84fcce2aa77095e6`.

Хеш сверяется и с официальным `SHASUMS256.txt`, и с фактически скачанным архивом. Несовпадение останавливает операцию до `apt` и распаковки. Архив удаляется после операции. Используются прямые HTTPS-файлы, а не непрозрачные `curl | bash` установщики.

Отдельная сборка размещается в `/opt/rikkahub/node-v24.22.1`. Изменяются только app-owned staging/backup-каталоги этой сборки. Существующие `.venv` и файлы проектов не перезаписываются.

Перед заменой отдельной сборки проверяются структура распакованного архива, исполняемые Node/npm и обе версии. Ошибка распаковки или проверки не удаляет прежнюю сборку. Если предыдущая операция прервалась после переноса старой сборки в backup, отсутствующий основной каталог сначала восстанавливается из этой копии. Staging удаляется после завершения скрипта, а ошибка замены вызывает откат.

## Критерии «Готово»

«Готово» присваивается только после успешных функциональных проверок:

- Python: версия `python3`, JSON и UTF-8, системный pip, создание временного venv, запуск его Python и `python -m pip`;
- Node.js: Node и npm с версиями, JavaScript с JSON и записью/чтением файла, поддерживаемый major 22/24.

Временные проверочные каталоги создаются через `mktemp` внутри Rootfs `/tmp` и удаляются через `trap`. Кнопка «Проверить» выполняет только локальные команды проверки: она ничего не скачивает и не переустанавливает профиль.

В настройках отображаются фактические состояние, версии, пути запуска, `exit_code`, причина ошибки и раскрываемая диагностика. Во время операции показывается недетерминированный индикатор без выдуманного процента.

## Команды для проектов

Активация venv не сохраняется между отдельными вызовами `workspace_shell`. Используйте явные пути:

```sh
/workspace/<проект>/.venv/bin/python
/workspace/<проект>/.venv/bin/python -m pip install ...
```

Для Node.js зависимости устанавливаются локально: `npm install` в каталоге проекта. `npm install -g` и изменение Root PATH запрещены. Для отдельной сборки PATH задаётся только одной команде:

```sh
PATH=/opt/rikkahub/node-v24.22.1/bin:$PATH <команда>
```

## Операции, отмена и восстановление

В одной рабочей папке одновременно допускается только одна операция профиля; повторное нажатие не создаёт дубликат. Разные рабочие папки независимы. Операции принадлежат application-scope и не перезапускаются при повороте экрана или повторном открытии страницы.

После нажатия «Остановить» новая операция допускается только по окончании очистки предыдущей. Обновление страницы не заменяет текущий статус или результат более старым снимком. Можно остановить и автоматическую проверку после прерывания: кнопки не остаются заблокированными в состоянии «Проверка».

Блокирующие скачивание, установка и файловые операции выполняются вне главного потока. «Остановить» отменяет только принадлежащий Job и его foreground PRoot/скачивание через `runInterruptible`; `stopBackground` и посторонние процессы не затрагиваются.

После гибели приложения сохранённые «Подготовка»/«Проверка» переводятся в «Прервано». Автоматически выполняется только повторная проверка, установка не возобновляется.

Generation marker и fingerprint Rootfs не дают сохранить устаревшее «Готово» после замены или удаления Rootfs, в том числе во время проверки. Успешная замена Rootfs сбрасывает метаданные профилей. Неудачная замена с подтверждённым откатом восстанавливает прежний generation marker и точное сохранённое содержимое метаданных Python/Node.

После скачивания Node.js Rootfs повторно сверяется до запуска apt и распаковки. Поздний результат не создаёт заново удалённую рабочую папку. Удаление папки также очищает отображаемые сведения профиля.

## Безопасная замена Rootfs

Кандидат скачивается, распаковывается и настраивается отдельно от действующей среды, в приватном каталоге рабочей папки `.rootfs-installer/staging`. Проверяются `/bin/sh`, `/usr/bin/env` и реальное выполнение проверочной команды через существующий PRoot runner с выбранным для рабочей папки режимом совместимости. До успешной проверки прежний Rootfs остаётся на месте.

Переключение использует два отдельных переименования: старый `linux` переносится в `.rootfs-installer/backup`, затем кандидат занимает `linux`. Это не одна атомарная операция. Журнал `.rootfs-installer/operation.json` сохраняет фазы и идентичности каталогов, прежний generation marker и метаданные профилей, чтобы восстановить состояние между переименованиями.

Точка подтверждения — сохранённая и проверенная запись `INSTALLED` для той же операции. До неё ошибка или отмена вызывают откат. Если запись журнала могла сохраниться, но вернула ошибку, решение принимается по заново прочитанному журналу. Нечитаемое или чужое подтверждение не даёт права ни объявить успех, ни автоматически удалить данные и выполнить откат.

После `INSTALLED` ошибка удаления backup не отменяет установку. Интерфейс показывает отдельное предупреждение об очистке; новый Rootfs и его generation остаются действующими. Следующее локальное восстановление повторяет только очистку принадлежащих операции каталогов. Каталог с неожиданной идентичностью сохраняется для диагностики.

После гибели приложения восстановление происходит локально перед доступом команды, профиля или терминала к Rootfs, а также при проверке целостности. Скачивание, установка и проверочная команда кандидата автоматически не возобновляются. Повторное восстановление безопасно. При неподтверждённом откате доступ к среде блокируется, а backup, кандидат и журнал сохраняются; прежняя среда не объявляется восстановленной.

Подтверждённый `ROLLED_BACK` отделяет восстановление прежних данных от последующей очистки. После этого новые результаты проверки профилей сохраняются; повторная очистка не заменяет их исходным снимком. Ошибка записи подтверждения отката проверяется повторным чтением журнала. Оставшиеся после гибели процесса временные файлы атомарной записи удаляются только по собственным именам с UUID, под блокировкой и до удаления основного журнала. Неизвестные данные сохраняются.

Проверка целостности снимает устаревший `INSTALLING`, когда файловая транзакция уже завершилась, а процесс не успел записать итог в базу. Действующая установка сохраняет этот статус под отдельной блокировкой. Публикация мини-приложения из Rootfs удерживает файловый доступ до завершения копирования исходников, поэтому смена Rootfs не смешивает файлы двух сред.

Одна рабочая папка допускает одну замену. Выполняющаяся команда, операция профиля, живой терминал или управляемый фоновый процесс отклоняют замену до скачивания. Интерфейс сначала запрашивает закрытие принадлежащих рабочей папке терминалов и ждёт фактического завершения. Timeout или отмена закрытия сохраняют учёт ещё живых сессий для повторной попытки. Процессы других рабочих папок не останавливаются.

Смена Rootfs не удаляет `/workspace`, исходники и файлы `.venv`. Установленные в старой Linux-среде системные пакеты заменяются вместе с ней; после успешной замены Python/Node нужно заново проверить или подготовить. Сохранённое `.venv` может требовать пересоздания при несовместимости версии Python или системных библиотек нового Rootfs.

Файловые операции, проверка кандидата и восстановление выполняются вне UI-потока. Эти гарантии проверяются JVM-тестами на реальных временных каталогах и переименованиях; поведение PRoot и Android-файловой системы дополнительно проверяется на телефоне. Восстановление покрывает остановку процесса приложения; аварийное обесточивание накопителя отдельно не моделировалось.

## Данные для модели

`WorkspaceReminderTransformer` использует workspace эффективного assistant текущего разговора, который формируется с учётом `ConversationConfig`. Модели передаются только компактные фактические состояние, версии и пути Python/Node/npm, а также правила локальных зависимостей. Диагностика, `rootfsStamp`, env, ключи и секреты не передаются.
