# Постоянная Root-сессия

По запросу владельца форка обычные Root-команды должны переиспользовать существующий
привилегированный транспорт, как фоновые команды. Сохранить literal command,
stdout/stderr, exit_code, ограничения вывода, пользовательский timeout и отмену
всей принадлежащей команде группы процессов.

Выбран предложенный пользователем минимальный вариант: расширить существующий
broker, без Shizuku/Sui, libsu, нового daemon или socket-протокола. Эти альтернативы
требуют замены уже проверенной остановки процессов и не нужны для устранения
повторного запуска su. Скорость на настоящем телефоне проверяется отдельно.

RootShellManager владеет одним транспортом и общей отменяемой очередью. Первый
обычный вызов после проверки UID открывает транспорт; следующие обходятся без
нового su и probe. Подготовленная фоновая сессия также используется обычными
вызовами. Фоновый доступ по-прежнему требует отдельной явной подготовки; обычный
вызов не выдаёт этот доступ. Фоновые задачи никогда сами не запускают новый su.

Каждая команда получает отдельные script, stdout, stderr и nonce и запускается
в отдельной оболочке/группе, поэтому exit/cd/export не меняют следующие вызовы.
Для обычных команд сохраняются прежний `sh -c`, `$0=sh` и исходная маска su;
фоновый режим сохраняет выполнение script-файла и прежний umask 077. При чтении
команды для `sh -c` sentinel сохраняет все завершающие переносы строк; ошибка
чтения не допускает исполнения частичной команды. Текст команды не исправляется.
Обычная завершившаяся оболочка сохраняет явно запущенных фоновых потомков, как
прежний однократный транспорт, включая ненулевой код выхода. Guardian проверяет
идентичность группы и отпускает только supervisor через отдельный release FIFO;
при таймауте/отмене он по-прежнему убивает всю принадлежащую запросу группу.
Фоновые задания сохраняют прежнюю строгую очистку и после обычного завершения.
Модельная оболочка и дренирование не наследуют completion/release дескрипторы.
Проверка разрешения повторяется после ожидания очереди и прямо перед отправкой.
Время команды считается после подготовки и ожидания очереди, как у прежнего
транспорта; ожидание очереди можно отменить.

Старый однократный транспорт остаётся запасным только если постоянный transport
не удалось подготовить ДО отправки пользовательской команды. После отправки
никаких повторных запусков: ошибка, timeout или потерянное подтверждение остаются
ошибкой с доступным частичным выводом. Неподтверждённая очистка закрывает транспорт.
close во время подготовки не должен воскресить закрытую сессию или запустить
запасную команду. Повторная явная подготовка имеет прежний жизненный цикл.

Broker читает ограниченные префиксы stdout/stderr отдельными блоками dd до 4096
байт, проверяя фактически записанный размер через wc после каждого короткого
чтения. Остаток продолжает дренироваться. Неподдерживаемый счётчик сохраняет
прежний ограниченный `bs=1`. `head -c` отклонён:
проверка с отделившимся потомком, удерживающим pipe, доказала потерю короткого
вывода из его буфера при принудительном завершении дренирования.
`dd count_bytes` также отклонён: при коротких чтениях он может исчерпать число
записей раньше нужного количества байтов. Обычный dd count=1 в цикле сохраняет
каждое короткое чтение сразу и не превышает общий байтовый предел.
Завершение команды уведомляет guardian через отдельный FIFO;
при поддержке fractional read timeout guardian получает событие сразу и между
ожиданиями по-прежнему проверяет отмену, таймаут, приложение и broker. На остальных
оболочках остаётся прежний файловый опрос. Поддержка проверяется до первого
запроса. Отдельного watchdog-процесса нет; его отказ не может оставить guardian
заблокированным. После чтения повторно проверяется active: позднее завершение
не отменяет истёкший таймаут. Модельная команда не наследует дескриптор FIFO.
Перед возвратом очищаются принадлежащая команде группа и группы дренирования.
Данные /proc читаются встроенным read вместо запуска cat для каждой проверки;
проверки start time, session/group identity и состояния Z сохраняются.
Нет снятия лимитов или молчаливой правки команд.

Не меняются applicationId, подпись, workflow, разрешения инструментов и поведение
Android API. Пакеты действий экрана, сокеты и отдельный daemon не входят в эту
задачу. Проверки и подписанный APK — существующий Daily Build; локально только
затронутые unit-классы и компиляция.
